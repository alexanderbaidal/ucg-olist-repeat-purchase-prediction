## Project overview

This is a graduate thesis project (Trabajo de Titulación, Maestría en Data Science e IA - UCG). It is not a software application — the deliverable is a data science case study consisting of two executed Jupyter notebooks plus a written technical report and defense presentation, both generated from the `plantillas/` Word/PowerPoint templates and checked into `entregables/`.

**Case:** "Personalización Data-Driven en E-Commerce" (fictional company "ShopMart"), solved using the public **Olist Brazilian E-Commerce** dataset (Kaggle, ~100k orders 2016–2018). Full case brief: [caso-de-uso/data-driven-e-commerce.md](caso-de-uso/data-driven-e-commerce.md).

**Angle chosen and implemented (documented inside NB1/NB2):** the Olist dataset is a static snapshot with no explicit churn label — only 3.1% of customers have more than one order. The project therefore predicts **`repeat_purchase`**: whether a customer's *first* order will be followed by a second one, using only features derivable from that first order (avoids temporal leakage). This is complemented by an RFM + clustering customer segmentation as a supporting analysis.

**Status:** both notebooks are implemented and have been executed end-to-end against the real dataset (no placeholder cells). Current result snapshot (see `notebooks/artifacts/model_card.json` for exact figures): final model is a tuned `HistGradientBoostingClassifier`, test PR-AUC = 0.059 vs. a 0.033 baseline (DummyClassifier), ROC-AUC = 0.63, lift = 2.27x in the top score decile. **Important, easy-to-misstate finding:** no individual feature — including `review_score` — has a meaningfully strong correlation with the target (all |Spearman ρ| < 0.03), and in the initial cross-validation comparison `LogisticRegression` and `HistGradientBoostingClassifier` are statistically tied (≈0.047 vs. ≈0.046 PR-AUC); the ensemble was chosen for its hyperparameter-tuning upside, not because it clearly won. When editing the notebooks, report, or slides, do not reintroduce a "review_score drives repeat purchase" or "the ensemble clearly beats the linear model" narrative — both were checked against the actual computed numbers and are false.

## Working with the notebooks

- **Run notebooks from inside `notebooks/`** — both notebooks use relative paths (`Path("dataset")`, `Path("artifacts")`) assuming that working directory, not the repo root.
- **Dataset sourcing (NB1, section 1):** if `notebooks/dataset/` already has the 9 Olist CSVs (the normal case — they're checked into the repo), NB1 uses them directly with no network call. If that folder is missing/incomplete, NB1 falls back to downloading via `kagglehub.dataset_download("olistbr/brazilian-ecommerce")`, which requires a Kaggle account/API token (env var `KAGGLE_API_TOKEN`) and caches to `~/.cache/kagglehub/`. Don't remove this fallback — it's what lets the notebook run on a machine without the CSVs pre-populated.
- **Execution order matters**: NB1 must be run fully before NB2 — NB2 loads `X_train/X_val/X_test`, `y_train/y_val/y_test`, `preprocessor.joblib`, and `eda_summary.json` from `notebooks/artifacts/`, all produced by NB1.
- **`RANDOM_STATE = 42`** is fixed at the top of both notebooks for reproducibility — preserve it when editing.
- The project `.venv` only has Jupyter kernel essentials installed (ipykernel, jupyter_client, etc.) — pandas/numpy/scikit-learn/seaborn are not in `pip freeze`. Check which Python environment/kernel the notebooks are actually configured to run under before assuming packages need installing; do not add a requirements file speculatively. (The Aug 2026 build/execution used an ad-hoc environment with `scikit-learn`, `pandas`, `seaborn`, `joblib`, `pyarrow`, `nbformat`/`nbclient`/`jupyter` installed via pip — the checked-in `.venv` itself was not modified.)
- No test suite, linter, or build tooling exists in this repo — there is nothing to run beyond executing the notebooks themselves. Validate changes by re-running the affected notebook end-to-end and inspecting outputs/artifacts.
- If you regenerate NB1 and/or NB2, the `.docx`/`.pptx` deliverables in `entregables/` go stale (they embed specific numbers and figures as static text/images, not live references) — regenerate them too, and re-check every claim in their text against the new `model_card.json`/`eda_summary.json` before considering the update done. Past mistake to avoid: writing a plausible-sounding narrative claim first and checking the numbers later — always pull the number from the notebook output before writing the sentence.

## Data flow contract (NB1 → NB2)

NB1 must persist to `notebooks/artifacts/`, and NB2 assumes as given:
- `X_train.parquet`, `X_val.parquet`, `X_test.parquet`, `y_train.parquet`, `y_val.parquet`, `y_test.parquet` — pre-processed splits, target column `repeat_purchase`.
- `preprocessor.joblib` — fitted `ColumnTransformer`/`Pipeline` (fit on train only — no leakage).
- `eda_summary.json` — key EDA findings consumed downstream.
- `raw_train/val/test.parquet`, `orders_history.parquet` — pre-transformation tables used for error analysis / RFM in NB2.

NB2 in turn produces `repeat_purchase_model.joblib`, `test_predictions.parquet`, `model_card.json` (metrics, hyperparameters, feature importances, known limitations), and `customer_segments.parquet` — these are the evidence base for the written technical report.

Primary model metric is **`average_precision`** (PR-AUC), because the positive class is rare (~a few percent repeat-purchase rate) — accuracy/ROC-AUC alone are misleading here. Preserve this choice when modifying evaluation code.

### RFM segment labels (NB2, customer_segments.parquet)

Segment labels (`recompradores`, `premium_recientes`, `en_riesgo_bajo_valor`, `bajo_ticket_reciente`) are assigned from each KMeans cluster's actual recency/frequency/monetary profile (see `label_segment()` in NB2), **not** by a fixed rank-by-monetary-value order. An earlier version of this notebook mapped labels by sorting clusters on `monto_medio` alone, which silently mislabeled the highest-recency (most dormant) cluster as `recompradores`. If you touch the clustering or labeling code, recheck the printed per-cluster profile table against the label each cluster receives before trusting it downstream.
